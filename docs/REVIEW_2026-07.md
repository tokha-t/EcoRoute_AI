## 2. Architecture — ADR-001

# ADR-001: Streamlit monolith for EcoRoute AI V1

**Status:** Accepted (reaffirmed)
**Date:** 2026-07-04
**Deciders:** solo founder

### Context
Pre-data MVP for an accelerator demo. One maintainer. No real sensor feed yet — data is synthetic. Needs to render a map, run a CVRP, and estimate fill from photos, live in a browser with zero ops.

### Decision
Keep the single-process Streamlit app; push all logic into importable, independently-tested `src/` modules; treat OSRM as an optional local dependency with a haversine fallback.

### Options considered

| Option | Complexity | Cost | Scalability | Team fit |
|--------|-----------|------|-------------|----------|
| A. Streamlit monolith (current) | Low | Free tier | Low (single session, in-proc) | Excellent (1 person) |
| B. FastAPI + React + worker | High | Hosting + build | High | Poor for now |
| C. Notebook / script only | Very low | Free | None | Loses the dispatcher UI |

### Trade-off analysis
The real engineering value — prediction, prioritization, CVRP, photo estimation — already lives in `src/` behind clean function contracts and is fully testable without Streamlit. The monolith is therefore a thin, replaceable shell, not a lock-in: you can lift `src/optimize`, `src/predict`, `src/photo_fill` into a service later with no rewrite. Cost is real but bounded: no concurrency, `@st.cache_data` is per-process, and heavy work (RF load, CVRP solve) runs in the request thread.

### Consequences
- **Easier:** iteration speed, deploy, testing.
- **Harder:** multi-user, background jobs, real-time sensor ingestion.
- **Revisit when:** a real data feed arrives, or >1 dispatcher needs concurrent access.

### Action items
1. [ ] Extract `app.py` logic helpers into `src/ui/` to keep the shell truly thin (supports a future service swap).
2. [ ] Decide OSRM hosting story for the public demo (currently `localhost:5000` → always falls back to haversine when deployed).
3. [ ] Retire `routing.py` once the comparison panel is on OR-Tools.

## 3. System Design — current state + what to revisit

### Data flow today

```
data_generator (SYNTHETIC) ─► training_data.csv ─► train_model (RF) ─► fill_level_model.pkl
                              └► bins.csv
                                     │
Streamlit UI ── load_bins ──► predict.predict_fill_levels ──► assign_priority (max-interval override)
     │                                    │
     │                              selected sites
     │                                    ▼
     │         optimize.distances.get_matrix ──► OSRM /table  (fallback: haversine×1.4, flagged)
     │                                    ▼
     │              optimize.solver.plan_routes (OR-Tools CVRP) ──► Plan
     │                                    ▼
     └── live-photo mode ─► photo_fill.estimator ─► Anthropic vision ─► observations ─► plan_routes
                                    savings.calculate_savings ──► KPIs (banner: "Simulated")
```

### Non-functional profile (V1)
~180 bins, single user, 5s solver limit, no persistence beyond CSV snapshots, no auth (by spec). All appropriate for a demo.

### What to revisit as it grows toward real deployment

- **Data source.** `data_generator` is the load-bearing fiction. V2 credibility hinges on replacing it with a real sensor/route-history feed — and the model was trained on a *known* synthetic generating function, so real-world MAE will differ materially from the reported 4.53. Retrain + re-baseline on real data before any measured claim.
- **State/persistence.** CSV snapshots (`sample_predictions.csv`) are overwritten each run and per-process cache won't survive multi-user. A small DB (SQLite → Postgres) is the first infra add when a second dispatcher appears.
- **OSRM.** In the deployed demo there's no `localhost:5000`, so it silently runs on haversine — correctly flagged, but every "road distance" shown live is really straight-line×1.4. Host OSRM (or a managed routing API) before distances are presented as road-accurate.
- **Cost/abuse boundary.** Photo mode = paid API behind a public URL (see Code Review #1). Needs auth or a hard quota before real exposure.
- **Cache invalidation.** The OSRM matrix cache is keyed on rounded coordinates with no TTL — fine for static bins, wrong once bins move or real-time traffic matters.

### Overall
The architecture is right-sized and, more importantly, honestly labeled — the code never presents simulation as measurement, the single most valuable property this project has going into an accelerator. The main risks are all at the seams where synthetic V1 meets real-world V2, and the clean `src/` boundaries mean those seams are addressable without a rewrite.

# AI-Firstify Assessment Report

**Project:** EcoRoute AI
**Date:** 2026-07-04
**Mode:** Audit (read-only)

> Framing note: AI-Firstify measures alignment with AI-first design principles (terminal-first, skills over embedded agents, context hygiene, safety, prescriptive workflows). EcoRoute is a *deployed product* rather than a Claude-Code-native automation, so a few dimensions are scored against that reality — a warranted frontend and one bounded LLM call are not penalized as anti-patterns, but genuine gaps (no skills, public API exposure) are.

| Dimension | Score | Summary |
|-----------|-------|---------|
| 1. Project Structure | 🟢 GREEN | 31-line CLAUDE.md, thorough .gitignore, milestone-tagged git history, clean monorepo layout |
| 2. Agent Architecture | 🟡 YELLOW | One Anthropic vision call in the core photo path — bounded and schema-strict, but a real in-app LLM dependency |

## Detailed Findings

### Dimension 1: Project Structure — 🟢 GREEN
`CLAUDE.md` is 31 lines: structure, commands, and hard rules, nothing bloated. `.gitignore` correctly excludes `.env`, `*.pkl`, `data/cache/`, `outputs/`, `.claude/settings.local.json`, and photo inboxes while whitelisting `labels.csv` and `config.toml`. Git is initialized with clean, milestone-tagged history (M0–M5). 17 root entries, logically grouped (`src/`, `tests/`, `docs/`, `data/`, `models/`). Code, data, docs, and tests live together — a proper monorepo.

### Dimension 2: Agent Architecture — 🟡 YELLOW
No agent framework (no langchain/autogen/crewai), no prompt-chaining, no embedded chatbot. The single LLM touchpoint is `photo_fill/estimator.py`: one constrained Anthropic vision classification with a server-side JSON schema, strict client-side parsing, one retry, and an `uncertain` escape hatch. That's a *good* bounded use, not an anti-pattern. It scores YELLOW rather than GREEN only because it's a live third-party API in the core product path with no offline fallback — if the API is down or the key is unset, live-photo planning can't run. Wrapping it behind an interface with a heuristic fallback would move this to GREEN.

### Dimension 3: Skill Usage — 🟡 YELLOW
A `.claude/` directory exists but contains only `settings.local.json` and `launch.json` — no `.claude/skills/`. Meanwhile the repo has several genuinely repeatable workflows: model retrain (`python -m src.train_model`), the dry-run QA checklist (`docs/DRYRUN.md`), the photo-dataset CLI, and the demo script. These are documented as prose/commands and a `CLAUDE_CODE_PROMPTS.md` pack, which is better than nothing, but none are packaged as prescriptive skills with `references/`. This is the clearest AI-first gap.

### Dimension 4: Scope & Complexity — 🟢 GREEN
The Streamlit frontend is warranted — the dispatcher-facing UI *is* the product. `requirements.txt` is lean (streamlit, pandas, numpy, sklearn, plotly, joblib, requests, ortools). No database, no auth, no deployment pipeline. `CLAUDE.md` explicitly bans DB/auth/FastAPI in V1, so scope discipline is codified, not accidental.

### Dimension 5: Context Hygiene — 🟢 GREEN
`CLAUDE.md` is well under the 200-line bar and organized (Structure / Commands / Rules). Large reference material — `SPEC_V1.md`, `DRYRUN.md`, `osrm-setup.md`, `REAL_SYSTEM_FRAMEWORK.md` — lives in `docs/`, not inlined. Minor: two framing docs sit at the repo root (`CLAUDE_CODE_PROMPTS.md`, `REAL_SYSTEM_FRAMEWORK.md`); moving them under `docs/` would be tidier, but this isn't pollution.

### Dimension 6: Safety — 🟡 YELLOW
Strong on code hygiene: no hardcoded secrets (scan hit only `.venv`), API key read from `ANTHROPIC_API_KEY` and never logged, `.gitignore` excludes `.env` and model artifacts, and the app only writes local CSV snapshots. Human-in-the-loop is real — `confirmed_observations` keeps `uncertain` photos out of the plan unless a dispatcher resolves them. The YELLOW is the deployment seam: the public `streamlit.app` demo exposes the paid vision call with no auth, quota, or upload guard (same as Code Review issues #1–#2). An external, billable action without an approval boundary is exactly what this dimension flags.

### Dimension 7: Workflow Design — 🟢 GREEN
Workflows are prescriptive: `CLAUDE.md` Commands section, `docs/DRYRUN.md` checklist, `demo_script.md`, and a Claude Code prompt pack. Validation is a real strength — 93 tests including a dedicated determinism suite, a GitHub Actions CI workflow, and ruff. Git commit discipline is evident (clean tree, coherent milestone commits). The only missing AI-first element is a dedicated sub-agent review/critique step; automated tests currently fill that role well.
