# PRD — EcoRoute AI Version 1 ("Pre-Data MVP")

**Owner:** Tokha (solo) · **Date:** 2026-07-02 · **Status:** Draft for tracker review
**Window:** 4 weeks build + 2–4 weeks polish/buffer before pilot
**Companion doc:** REAL_SYSTEM_FRAMEWORK.md (V2 = with Tazalyk data)

---

## 1. Problem Statement

EcoRoute AI currently demonstrates its loop (predict → select → route → savings) on synthetic data with a model that cannot generalize to reality. Trackers, jury, and Астана Тазалық will all ask the same question: *"Where does the AI get real data?"* Today there is no defensible answer. V1 must make every technical claim in the pitch demonstrably true **without needing anything from the operator**, so the project stays fully unblocked while data negotiations run in parallel.

## 2. Version Strategy (answers the dependency question)

- **V1 (this spec): zero operator dependency.** Photo-based fill detection trained on self-collected photos + real road routing + honest simulation sandbox. Everything buildable alone, this month.
- **V2: operator data plugs into V1.** Their driver photos feed the same photo model; their GPS feeds visit history; their registry replaces the self-built one. V1 is designed so V2 is a data swap, not a rebuild.
- Hard dependency on Tazalyk exists only for one thing: **proving savings on their fleet** — which is the pilot itself, and inherently requires them anyway.

## 3. Goals

1. Photo→fill-level model reaches **≥85% accuracy (macro-F1 ≥0.80) on 4 classes** (empty / ~half / full / overflowing) on a held-out set of *sites the model never saw*.
2. Routing engine produces routes on **real Astana roads** (not straight lines) with **truck capacity and shift-length constraints**, solving 300 sites in <30 s on a laptop.
3. Live demo flow: photograph a real container site → model scores it → site enters today's route → savings recomputed. End-to-end in <3 minutes, works offline from venue Wi-Fi (local fallback).
4. Every number said to jury/tracker is generated by code in the repo, with the synthetic parts explicitly labeled "simulation."

## 4. Non-Goals (V1 will NOT do)

- **No operator data ingestion** (GPS parsers, weighbridge, ИС Waste Management integration) — that's V2; building parsers before seeing real formats wastes time.
- **No trained fill-forecasting ML** — forecast quality is untestable without real service history; V1 ships the accumulation baseline with adjustable rates as simulation.
- **No driver app / Telegram bot** — build it days before pilot start, not now (2–3 days of work, avoids maintaining unused software).
- **No sensors, no hardware** — photos replace them; core product thesis.
- **No multi-city, no auth, no cloud backend** — Streamlit monolith stays; FastAPI split is V2 when a second consumer (bot) appears.

## 5. Users & Stories

**P1 — AIA jury / tracker (demo audience)**
- As a tracker, I want to see the AI read a real photo of a real Astana container, so that I believe the data story without a sensor procurement fairy tale.
- As a jury member, I want savings claims labeled simulation vs. measured, so that I can trust the founder's other numbers.

**P2 — Dispatcher (simulated persona, future buyer)**
- As a dispatcher, I want today's route to always include any site overdue by more than N days regardless of prediction, so that no bin ever rots (max-interval rule).
- As a dispatcher, I want routes that respect truck capacity and shift length, so that the plan is physically executable.
- As a dispatcher, I want to force-include or exclude a site manually, so that local knowledge beats the model when needed.

**P3 — Founder-as-data-collector**
- As the founder, I want a phone-friendly capture flow (photo + site ID + label), so that I can build the training set in field walks without post-processing chaos.

## 6. System Design (technical aspects)

### 6.1 Components

```
[Photo Capture] → [photo_fill/  CV service]───┐
                                              ▼
[Site Registry (self-built, 1 district)] → [prediction/  v0 accumulation + overrides]
                                              ▼
[OSRM (Docker, kazakhstan.osm.pbf)] → [optimize/  OR-Tools CVRP] → [Streamlit UI: Simulation mode | Live-photo mode]
```

### 6.2 Photo fill detection (`src/photo_fill/`)
- **Dataset:** 150–300 sites × 1–3 photos, self-collected in one district. Capture protocol: whole container visible, 2–5 m distance, note site_id + timestamp; shoot mornings (pre-collection). Label 4 classes; two-pass self-labeling on different days for consistency; ~10% relabeled by a friend for agreement check.
- **Storage:** `data/photos/{site_id}/{ts}.jpg` + `labels.csv` (site_id, ts, class, labeler).
- **v0 model:** VLM API (structured prompt → class + confidence + visible-issues). Prompt-engineer against labeled set.
- **v1 model (only if v0 <85%):** fine-tune a small ViT/CNN classifier (few hundred images is enough for 4 classes with augmentation).
- **Eval:** split **by site**, never by photo (photos of one site are near-duplicates; splitting by photo inflates accuracy). Report per-class confusion matrix. Winter/night degradation documented as known limitation.
- **Interface:** `estimate_fill(image) -> {class, pct_range, confidence}`; confidence < threshold → route to "manual check" list, never silently guessed.

### 6.3 Routing engine (`src/optimize/`)
- **Distances:** OSRM in Docker with `kazakhstan-latest.osm.pbf`; `table` API for the travel-time matrix; cache matrices per site-set hash. Fallback to haversine×1.4 detour factor if OSRM is down (demo insurance, flagged in UI).
- **Solver:** OR-Tools `RoutingModel`: capacity dimension (kg and m³ with per-truck compaction ratio), shift-duration dimension, mandatory-visit set (max-interval violations + Critical predictions + manual pins), 1–3 vehicles, depot start/end. Landfill mid-shift dump = P1 (refill node), not P0.
- **Contract:** `plan_routes(sites, trucks, constraints) -> routes + total_km + violations[]`. `violations` must be empty to render a plan.

### 6.4 Prediction v0 (`src/predict/`)
- Accumulation: `fill(t) = fill_after_last_visit + rate_site × hours`; rates from editable per-district priors (UI sliders) — explicitly labeled simulation until V2 data.
- **Max-interval rule (P0):** `hours_since_collection ≥ N×24 → priority = Critical, must_serve = True`. Default N=3, configurable.
- Output is overflow-risk band, not fake decimal percent.

### 6.5 App changes (`app.py`)
- Mode toggle: **Simulation** (current 180-bin sandbox, relabeled honestly) | **Live photo** (upload/capture → 6.2 → site joins plan).
- Savings panel: "simulated estimate" watermark in simulation mode; target range 15–25% cited from meta-analysis, not 87%.
- Keep Streamlit; extract CSS to `assets/styles.css` (audit item).

### 6.6 Repo & quality
- `tests/__init__.py` fix; unit tests for routing (known-distance, capacity respected, must-serve honored) and photo interface (schema, low-confidence path). CI: GitHub Actions running pytest.
- Rename repo → `EcoRoute_AI`; update links in README/deck.

## 7. Requirements Summary

**P0 (ship-blockers):** photo model ≥85% w/ by-site eval · OSRM road distances · OR-Tools capacity+shift+must-serve · max-interval rule · mode toggle with honest labeling · tests+CI green · demo runs offline-tolerant <3 min.
**P1:** landfill dump-trip modeling · manual include/exclude pins · confusion-matrix page in app (great tracker moment) · matrix caching.
**P2 (design-for, don't build):** driver Telegram bot · operator data adapters (GPS/registry/photos) · FastAPI split · LightGBM forecaster.

Acceptance checks (samples):
- [ ] Given a photo of an unseen site, when uploaded, then class + confidence render in <10 s and low-confidence goes to manual list.
- [ ] Given a site overdue ≥N days with predicted fill 10%, when planning, then it is in the route (max-interval beats model).
- [ ] Given 300 sites and 2 trucks of 5 t, when planning, then no route exceeds capacity or shift length, and total km uses road distances.
- [ ] Given simulation mode, when savings render, then "simulated" labeling is visible without scrolling.

## 8. Data Dependencies & Contingency (V2 outlook)

Ranked by importance to the pilot; V1 needs **none** of these.

| # | Data from Tazalyk | Importance | If refused/limited — fallback |
|---|---|---|---|
| 1 | Container-site registry (coords, container counts/types) | **Critical** | Self-build for ONE district: OSM/2GIS + a week of field walking (you're photographing sites anyway — same walk) |
| 2 | Truck GPS traces (2–4 wks sample) | **High** — visit history + baseline km for savings proof | Route sheets + ride-alongs; driver bot check-ins; baseline km from fuel/odometer reports |
| 3 | Driver before/after photo archive | **High** — instant label goldmine | Your own photos + bot-collected photos during pilot; model improves slower, still works |
| 4 | Collection schedules / route sheets | **Medium-high** — cheap for them, low-sensitivity; gives service intervals | Observe pilot district for 1–2 weeks (when trucks come = schedule) |
| 5 | Weighbridge per-trip tonnage | **Medium** — calibrates rates, enables km/tonne KPI | Container-count × density estimates; tonnage KPI dropped from pilot report |
| 6 | Fleet params (truck capacities, depot & landfill coords) | **Low effort/needed** — one meeting | Public info + truck spec sheets |
| 7 | iKomek complaints | **Low-medium** | Request from city (not operator) separately; or skip — photos cover overflow labels |

**Minimum viable pilot dataset = #1 + #4 (+ any one of #2/#3).** Everything else upgrades quality, not feasibility.

**Escalation ladder if they give nothing:**
1. **Shadow pilot** (no permission needed): self-built registry for one district, observe their trucks 2 weeks, run EcoRoute plans in parallel on paper, publish km comparison + photo-model accuracy. Credible accelerator deliverable.
2. **Switch partner:** private operators serve some Astana zones; satellite towns (smaller akimats) approve faster; a private hauler wanting to win a tender has the sharpest incentive.
3. **Reframe deliverable:** sell the **data audit** ("here's what your GPS+photos could save you") as pilot phase 1 — turns their data hesitancy into the product.

## 9. Success Metrics

- Leading: photo model macro-F1 ≥0.80 (stretch 0.85) by-site split · demo completion <3 min, zero crashes in 3 consecutive dry runs · tracker can answer "where's the AI?" after demo without your help.
- Lagging (pilot-gated): overflow rate ≤ baseline · mean fill-at-pickup 70–85% · km/tonne −15% vs baseline · 0 max-interval violations.
